Support tip: Why Windows driver recommendations may vary between deployment rings

Saved for offline reading · Open original ↗

By: Dorin Mardari – Sr Technical Support Engineer | Microsoft Intune

Managing Windows driver updates across deployment rings might give results that seem inconsistent. You might expect the same update to behave the same way everywhere, but Windows Update evaluates updates separately for the devices in each ring. As a result, the update might appear under Recommended drivers in one ring and Other drivers in another, change classification over time, arrive at different times, or not appear at all even though the manufacturer's website lists it for your devices.

In most cases, this behavior is expected. This article explains why it happens, what it means when you approve and deploy drivers, and how to tell expected behavior from a problem that needs Microsoft Support.

Intune and Windows Autopatch don't decide whether a driver is recommended.

  1. First, the publisher submits the driver. Many drivers are built by a component maker, such as a chipset, audio, or graphics vendor, but published to Windows Update by the original equipment manufacturer (OEM). The publisher decides which hardware the driver targets and whether it's marked as required. Only drivers marked as required can appear under Recommended drivers.
  2. Windows Update then evaluates each device. Windows Update decides whether a driver applies, and how it ranks against other drivers that also apply. It bases this on the device's hardware IDs, currently installed drivers, the Windows version, and the publisher's targeting rules.
  3. Finally, Intune shows the result for each policy. Each policy's driver list is built from the results for the devices assigned to it.

A driver isn't classified once for your whole tenant. Instead, it's classified for each policy (ring), based on the devices in that policy. Two devices can get different results for the same driver depending on their model, already installed drivers, and Windows version, even within the same ring. When the devices are in different rings, each ring can show the driver differently. This is especially common for drivers that apply to several device models.

If a driver is recommended for at least one device in a policy, the policy shows it under Recommended drivers, even if it's only optional for the other devices.

Example:

  • Ring A contains Device 1 and Device 2. The driver is recommended for Device 1 and optional for Device 2, so Ring A shows the driver under Recommended drivers.
  • Ring B contains only devices like Device 2, so Ring B shows the same driver under Other drivers.

Both rings can be managed the same way and contain similar hardware, but they show different results because of one device.

Each driver published to Windows Update has a unique UpdateID. You can find it in the driver's Update Details in the Microsoft Update Catalog. The same driver name and version can be published several times, for example for different devices or components, or with different requirements. Each of these publications is a separate update with its own UpdateID.

Windows Update can also deliver one update to several groups of devices, called flights. Flights are based on details such as the manufacturer, hardware, installed drivers, and Windows version. During a driver's rollout, Windows Update can change how the driver is ranked, for example from optional to recommended. Changes can be triggered by events such as a new driver dependency or an operating system update, and they can apply to the whole update or to one flight only:

  • If the change applies to the whole update, the driver moves to Recommended drivers in every ring that has devices it applies to.
  • If the change applies to one flight only, the driver changes only in the rings that contain devices from that flight.

This is why a driver can move from Other drivers to Recommended drivers in one ring, stay unchanged in another, or even move back again later.

To check which flight a device is in, run Get-WindowsUpdateLog on the device and search the generated WindowsUpdate.log for the driver's name or UpdateID. The entry shows the UpdateId and the FlightId, for example:

Title=Mediatek Inc. Bluetooth Driver Update (1.1146.0.608), ProductName=(null), UpdateId=09FA9654-A73F-4DF4-8691-81543A9E577E.1, FlightId=RD:000000, DeploymentID=000000000, DeploymentAction=Install, ClientMetadata: audience=(null), admin=(null), update=(null)

Two devices with the same UpdateId but different FlightIds are in different flights and can show the same driver differently. A device's FlightId can also change after the driver's ranking changes. You can't choose or change a device's flight. Use this information to compare devices across rings, or include it when you contact Microsoft Support.

For more information about how drivers roll out, see Gradual rollout – Windows drivers.

Whether a driver is recommended for a device can depend on what's already installed. For example, a device running a generic driver might get the manufacturer's driver as recommended, while a device that already has a manufacturer driver might get the same update as optional.

Different versions of a driver often have identical names. The same driver version can also be published more than once, for example with a different driver date or targeting different hardware. Each publication is a separate update, with its own classification and “Applicable devices” count. Use the “Version” and “Release” date columns to make sure you're comparing the same update.

Driver names in Intune are generated from information in the driver package. Since February 2026, they use the format Provider Class Driver Update (Version), for example Lenovo Ltd. Firmware Driver Update (1.0.0.31). Drivers published before then may show an older naming format. Names also might not match the ones used on the manufacturer's website or in other tools – (for example, a BIOS update shows as Firmware).

To match a driver, compare the version and, if needed, search the Microsoft Update Catalog for the driver's UpdateID. The UpdateID identifies one specific update, even when several updates share the same name and version. The Catalog's Driver Model field can also help, but its accuracy depends on how clearly the publisher describes the device in the "Models" section of the driver's INF file.

The Applicable devices count shows how many devices in the policy can install that specific update. It can be lower than the number of devices of the same model for a few reasons:

  • The update applies only to devices that match its targeting and don't already have a newer or better-matching driver.
  • The same driver might be split across several updates, each with its own count.
  • Inventory depends on each device’s Windows Update scan. Healthy devices can take up to 24 hours to complete their daily scan, after which Intune processes the results. This is not a guaranteed 24-hour limit for the complete inventory refresh.

A previous version's count isn't a reliable indicator of how many devices a new version applies to.

Windows Driver Update Policies FAQs. A driver can also be missing, or arrive later in some rings, for the following reasons:

  • Scan and processing timing: the driver only appears once an applicable device in that ring has scanned and the backend has processed it.
  • It doesn't target your devices. Windows Update checks the device's hardware IDs. For firmware and some other drivers, it also checks computer hardware IDs (CHIDs), which identify the specific system model.
    • If the publisher didn't include your model's identifiers, the driver isn't offered to it, even if the manufacturer's website lists it for that model.Only the publisher can fix this by republishing the driver.
    • Recommended does not guarantee that the selected update is the OEM’s preferred CHID-targeted release. Windows driver update policies have a documented CHID-targeting limitation. See Understand driver update approval behavior. For more information about CHIDs, see Using Computer Hardware IDs (CHIDs).
  • A better-matching driver is available for the device, so this one isn't offered.
  • It isn't on Windows Update. Not every driver on a manufacturer's website is submitted to Windows Update. Some manufacturers also stop publishing newer versions of certain drivers to Windows Update.
  • The device is new to the policy. After a device is assigned, it can take up to 24 hours to register for driver management. Approved drivers are then offered at the device's next update scan.
  • The Windows driver update policies FAQ has additional information why older drivers disappear from a policy.

As described and detailed above, this means the following behaviors may be expected:

  • The same driver is listed under Recommended drivers in one ring and under Other drivers in another.
  • A driver moves between the Recommended drivers and Other drivers lists over time, in some rings but not others.
  • A driver appears in one ring before another.
  • The number of drivers in a policy goes up and down as drivers are replaced or age out. This is more noticeable in small test groups than in large production rings.
  • A driver available on the manufacturer's website doesn't appear in your policies.

In policies with automatic approval, only drivers in the Recommended drivers list are approved automatically. As a result:

  • The same driver can deploy automatically in one ring and wait for review in another.
  • A driver can start deploying automatically in a ring if it moves into the Recommended drivers list.

This can break the release order you planned across your rings. To keep control:

  • To deploy a driver to every ring on your planned deployment schedule: Approve it manually where it's listed under Other drivers, and set the Make available in Windows Update date to match your plan.
  • To make sure your rings follow a strict order: Consider manual approval for later rings, so drivers deploy only when you approve them. Approve each driver after it's validated in earlier rings.
    • In Windows Autopatch, you can choose Automatic or Manual mode per deployment ring.
    • Switching an existing ring between modes creates new policies and removes existing approvals, paused drivers, and declined drivers for it. Plan the change before you make it. For more information, see Manage driver and firmware updates.
  • To hold a driver back everywhere: Pause it in every policy where it's approved. Don't rely on its classification, because it can change.
  • Remember that only the latest approved version installs. If a ring has a newer approved version of the same driver, that version installs instead. More details on the pause behavior: How quickly are paused updates actually paused?
  • To compare rings: Use the Windows Driver updates report, which shows one driver update across all your policies. For more information, see Reports for Windows driver update policies.
  • Keep each device in one policy. For more information, see the Windows driver update policies FAQ.
  • Ask the manufacturer. Check whether the driver was published to Windows Update for your model, and whether your model's identifiers were included. Only the publisher can check its submission and republish a driver. For more information, see Get support for the Hardware Program & Hardware Dev Center.
  • Check what Windows Update offers the device directly. Run the following commands in an elevated PowerShell window on an affected device. They ask Windows Update for applicable drivers, independently of Intune.
powershell
$session  = New-Object -ComObject Microsoft.Update.Session
$searcher = $session.CreateUpdateSearcher()
$searcher.ServiceID       = "9482F4B4-E343-43B6-B170-9A65BC822C77"
$searcher.SearchScope     = 3
$searcher.ServerSelection = 3
$results = $searcher.Search("Type='Driver' and IsInstalled=0")
$results.Updates | Select-Object Title, DriverModel, DriverVerDate, DriverHardwareID

 

If the driver isn't listed, it's either already installed or Windows Update doesn't consider it applicable to that device, regardless of the management tool. Check the installed driver version (for example, in Device Manager or the device's Windows Update history) before contacting the manufacturer.

  • If you need the driver urgently, deploy it outside of driver update policies, for example as a Win32 app or with the manufacturer's tools.
  • If a version is causing problems, pause it in your policies.

Microsoft Support can't check or speed up a driver submitted by a manufacturer. For publishing status or missing model identifiers, contact the manufacturer directly.

The following symptoms can indicate a service issue rather than expected behavior, so contact Microsoft Support:

  • Many drivers disappear from all your policies at the same time, and they aren't older than the versions installed on your devices.
  • New drivers don't appear in any of your policies for an extended period, although Windows Update offers them to the same models.
  • Applicable devices counts stay unexpectedly low for several days for drivers that the device check shows as applicable.
  • An approved driver doesn't show a deployment date, or isn't installed on applicable devices that are scanning for updates.

When the same driver shows under Recommended drivers in one ring and under Other drivers in another, it's usually because Windows Update evaluates each device separately and can change a driver's ranking for some devices only. Missing drivers are usually caused by rollout timing or by how the manufacturer published the driver.

You can't control how a driver is classified, but you can control what's deployed:

  • Approve drivers from the Other drivers list where needed.
  • Use manual approval where release order matters.
  • Pause drivers you don't want.
