A guide to governing local AI agents with Intune

Saved for offline reading · Open original ↗

See how Microsoft Intune helps discover supported local AI agents, govern access, protect work data, and set boundaries.

Local AI agents are becoming part of everyday work. Employees may use them on managed devices to access repositories, analyze files, automate tasks, or interact with external services. IT needs to understand which agents are present, decide how to handle them, and apply controls that match their approved use.

Our Ignite 2026 roundup of what's new in Microsoft Intune introduced new controls for agent governance and containment on managed devices. This hands-on follow-up explains how to put them to work.

No single control fits every agent or task. Coverage depends on the agent, host app, platform, and available signals. As always, test policies to understand behavior before deploying broadly.

Microsoft Agent 365 combines available inventory and runtime signals from Microsoft Defender, Intune, and Microsoft Entra to help IT identify supported local AI agents on Windows devices. Intune’s application inventory can help IT identify how and where discovered agents are installed. Admins can create a configuration profile that specifies which app inventory properties to collect and assign it to device or user groups. App inventory collects registered Win32 and Windows Store apps from Windows 10/11 devices that are Intune enrolled and Entra joined.

For an unwanted agent or app, note the Platform-specific app ID attribute. This is the MSI product code for Win32 apps or the package full name for Store apps. Admins can use this value to enable restrictions with a software compliance policy.

Local AI agents do not always map one-to-one with a host app. Currently, only host apps installed as Win32 or Windows Store apps appear in Intune’s app inventory.

Intune software compliance policy, available in public preview, can help restrict device access to protected company resources when a specified unwanted application is detected and applicable Conditional Access requirements are configured.

Software compliance evaluates installed apps by supported identifiers, not agent identifiers directly. Agents with multiple supported host apps may need multiple restricted software entries. Review these relationships before assigning the policy. In this preview, editor extensions, npm packages, and standalone executables aren't available to select.

Using the MSI product code or package full name of an unwanted app:

  1. Create a software compliance policy in the Intune console
  2. Add the app’s identifier as a restricted software entry
  3. Assign the policy to a device or user group
  4. Ensure a Conditional Access policy is configured to require that devices are compliant to access corporate resources

Once deployed, Intune marks targeted devices non-compliant if restricted software is found, allowing Conditional Access to block access to protected corporate resources across the entire device, even while the agent is inactive. After uninstalling the software, employees can immediately request a compliance check; once Intune confirms compliance with applicable requirements, access can be restored according to the organization’s Conditional Access policies.

To provide instructions for the employee, admins can create a custom message explaining why the device is out of compliance and how to fix it. The IT team can then use reporting to see which devices still need attention and adjust the policy as needs change.

App protection policies help control how work data is accessed and transferred within supported AI apps on iOS/iPadOS and Android, with or without device enrollment. Supported AI applications, including eligible offerings from Microsoft and third-party developers, can integrate with Intune app protection policies through the Intune App SDK. To get started:

  • Check the Microsoft Intune protected apps list, the Apple App Store, or Google Play to confirm which AI apps support Intune app protection policies.
  • Create or update an app protection policy for iOS/iPadOS and Android that includes those apps.
  • Configure data protection settings, such as limiting cut, copy, and paste and saving to personal storage, and access requirements such as a PIN.
  • Add conditional launch checks, then assign the policy to the user groups that use those apps.

An agent may be approved for a task without needing access to everything on the device.

Microsoft Execution Containers (MXC), now generally available on Windows 11, lets developers run each agent task inside a policy-driven execution boundary. Windows enforces the configured execution boundary independently of the agent, helping prevent supported agents and their generated code from exceeding the permissions established for the container. Developers choose how to contain their agents; IT sets the guardrails through the new agent containment policy in Intune.

On managed Windows devices, this policy defines the most an MXC-enabled agent can do. Setting the guardrails takes three steps:

  1. Define the ceiling in the Intune admin center under Endpoint security, in Agent containment.
  2. Configure folder access as deny, read-only, or read-write. Decide whether the agent gets network access, such as local loopback or external connections.
  3. Target the policy to all known MXC-enabled agents, or to a specific supported agent.

When an agent asks Windows to create a container, Windows compares the request with the Intune ceiling. Requests within the ceiling are granted. Requests that exceed it are denied, and the agent gets enough information back to adjust.

For example, IT might allow an agent to work in a project repository while denying access to a credentials folder. Initial coverage includes process containers and MXC-enabled agents that Microsoft Defender identifies, beginning with GitHub Copilot CLI and OpenAI Codex CLI.

The Windows 365 for Agents security baseline provides Microsoft-recommended device security settings for agent Cloud PCs. Protections apply as soon as a Cloud PC is provisioned and enrolled in Intune, before the agent signs in and starts working. The baseline provides Microsoft-recommended settings for Windows 11, Microsoft Edge, and Microsoft Defender for Endpoint, covering Defender Antivirus, Defender Firewall, attack surface reduction, credential protection, browser security, and OS hardening.

In the Intune admin center, go to Endpoint security > Security baselines and select Windows 365 for Agents Security Baseline. Review and adjust the default settings. Assign the profile to the device groups that contain the agent Cloud PCs. Restrict unneeded agent runtimes on Windows devices.

Many local AI agents rely on runtime environments like Node.js or Windows Subsystem for Linux (WSL). On Windows devices where these runtimes aren't needed, the Local AI Agent Baseline - OpenClaw (Preview), introduced in May 2026, can help disable or restrict them. It configures Windows Subsystem for Linux (WSL) settings and adds two firewall rules that block outbound TCP connections from Node.js executables.

Test the baseline configuration before deployment. Disabling WSL or blocking Node.js network traffic may impact more than OpenClaw and could be disruptive for employees who use these runtimes. To deploy it in the Intune admin center:

  1. Go to Endpoint security > Security baselines, select Local AI Agent Baseline - OpenClaw (Preview), and create a profile.
  2. Review each setting and turn off any that would disrupt legitimate work, such as on developer devices that rely on Node.js or WSL.
  3. Assign the profile to a pilot group first, then expand.

Intune can restrict agent execution on supported Macs and enable runtime protections for supported agents on Windows.

On supervised Macs running macOS 27 or later, Allowed Binaries and Denied Binaries control which apps and command-line tools can execute. For approved agents that support managed configuration, Intune can deliver policies governing tool permissions, MCP connections, approval requirements, and supported sandbox settings. Applicable macOS privacy controls provide another layer around access to sensitive data and device capabilities. The new app privacy permission defaults streamline consent, but they are not enforced restrictions.

For customers using Microsoft Entra Internet Access, Global Secure Access adds outbound network controls. Intune can deploy and configure the Mac client, while Entra policies restrict destinations for traffic routed through the service. Customers should configure traffic acquisition, bypass rules, and connection-failure behavior to match their security requirements.

These controls do not create a universal containment boundary around every agent or integration: coverage depends on the agent’s supported policies, its execution environment, and the traffic captured for enforcement.

Use Intune to enable Microsoft Defender AI agent runtime protections on managed Windows devices. For supported agents and event interfaces, such as Claude Code, Codex CLI, and GitHub Copilot CLI, Defender inspects designated interaction points to help identify prompt injection attempts. It can also block certain detected high-risk actions before execution.

Before starting, confirm that the organization has a Microsoft Defender for Endpoint Plan 2, Microsoft 365 E5, Microsoft Agent 365, or Microsoft 365 E7 license. Devices need to be onboarded to Defender for Endpoint.  Microsoft Defender Antivirus needs to be in active mode, with real-time protection turned on.

Admins can follow these steps:

  • In the Intune admin center, go to Endpoint security > Antivirus and select
    ‘Create policy’.
  • For Platform, select Windows. For Profile, select Microsoft Defender AI agent runtime protection.
  • Set AI Agent Protection to Audit and assign the policy to a small group of devices where supported agents are actively used.
  • Review detections in the Microsoft Defender portal for one to two weeks. In audit mode, informational alerts show what would have been blocked.
  • When the detections look accurate, change the setting to Block for the device groups where enforcement is required.
  • Confirm the effective setting on the device page in the Defender portal, then run the AI agent runtime protection demonstration on a test device.

With runtime protection enabled in block mode, employees can continue using supported agents, although certain detected requests or actions may be blocked according to the configured protection settings.

When Defender detects a prompt injection attempt inside a prompt or tool response, it can block the request before the agent acts. In Claude Code, the employee sees a Microsoft Defender block message and a Windows notification. The detection appears in Windows Security under Protection history. The security team sees a Suspicious AI prompt injection alert in the Defender portal.

Choose the controls that apply to the devices and agents. This checklist follows the post's structure rather than a required deployment sequence.

  1. Use app and local AI agent inventory in Intune, along with Defender and Agent 365 discovery.
  2. Use software compliance policies with Conditional Access to block access to company resources until compliance is restored. Protect work data with app protection policies for supported AI apps built with the Intune App SDK.
  3. Preview the agent containment policy for MXC-enabled agents. Ask agent vendors to support MXC and expose settings IT can manage. For agents running in Windows 365 for Agents Cloud PCs, deploy the Windows 365 for Agents security baseline.
  4. Deploy the Local AI Agent security baseline on Windows devices where agent runtimes aren't needed.
  5. On managed macOS devices, use denied binaries to block unwanted agents. Deploy configurations and enable network settings for approved agents.

With software compliance in preview, start with a small group of Windows devices. Before expanding assignments, validate host-app detection, the resulting compliance state, and how configured Conditional Access policies restrict and restore access. Agree how endpoint and security teams will handle findings and exceptions.
